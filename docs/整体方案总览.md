# Code Runtime Analyzer 整体方案总览

> 这是当前有效的总方案。第一次使用工具，请先看 [新手从这里开始](新手从这里开始.md)。

## 1. 大白话先说结论

这套产品不是“一个编辑器小插件”，而是四部分协作：

1. **独立后台**：管理产品字典、本次 CSV、历史查询、窗口连接、缓存和以后增加的模块能力；
2. **编辑器扩展**：读取用户当前正在看的代码，向编辑器已有的语言服务询问类型、定义、引用和函数调用关系，并在代码行末展示历史值；
3. **Web 工作台**：展示函数关系、历史证据和以后用户自定义的产品功能模块；
4. **OpenCode / AI 接口**：通过 MCP 使用同一个后台，不复制字典、CSV 和业务规则。

当前阶段只做**编辑器在线**：用户已经用实际编辑器打开代码仓，扩展和这个窗口保持连接。编辑器不在线时独立扫描整个代码仓的方案先不做，也不要求用户为了本工具生成 `compile_commands.json`。

## 2. 当前架构

```text
                         OpenCode + AI
                               │ MCP
                               ▼
编辑器窗口与扩展 ◀────── 独立后台与证据服务 ──────▶ Web 工作台
  │ 当前代码内容              │                       │
  │ 定义/类型/引用/调用关系    │ 字典、CSV、会话、缓存 │ 函数图、历史证据、模块
  └──────── 窗口专属语义通道 ─┴──── 窗口专属定位通道 ─┘
```

后台仍然是产品核心，但“当前代码到底是什么类型、函数调用谁”这类编辑器在线问题，由后台转发给**打开该代码仓的那个编辑器窗口**。这样可以直接复用公司定制编辑器已经理解的工程配置，不在 Windows 上重新猜 Linux、WSL、宏和头文件路径。

## 3. 为什么不写死 Microsoft C/C++ 或公司扩展

我们不知道用户安装的是 Microsoft C/C++、clangd，还是公司自己做的语言扩展。因此不按扩展名字、产品名字或版本号猜能力。

扩展实际请求当前编辑器提供的标准能力：

- 读取文档符号；
- 跳转定义；
- 查询类型定义；
- 查询引用；
- 查询函数调用层级；
- 读取行内提示（只作辅助证据）。

谁在背后回答并不重要。公司定制语言扩展如果能回答，就直接使用；回答不了的能力会显示为部分可用或暂不可用。安装包清单中的最低 API 版本只是为了让编辑器决定“这个 VSIX 能不能安装”，不能代替真实能力检测。

## 4. 自动兼容性检测

用户不需要凭肉眼判断。

打开 C/C++ 文件后，面板会自动显示一句短结论：

- **可以使用**；
- **部分可用**；
- **等待检测**；
- **暂不可用**。

点开详细报告后，每一项都同时说明：

1. 这项能力是什么意思；
2. 系统刚才实际检查到了什么；
3. 缺失后会影响什么；
4. 用户现在应该怎么做；
5. 需要排查时可复制的技术信息。

检测结果来自实际请求，不来自编辑器或扩展名称。语言服务仍在建立索引时可以重新检测，不要求重新安装。

## 5. 字段历史值怎样保证不匹配错

字典只保存稳定身份，例如 `school::Student::age`、全局符号和仓库内的相对定义路径，不依赖局部变量叫 `stu`、`a` 还是指针。

扩展只在当前可见文件中寻找字典涉及的候选名字，再让编辑器返回真实定义位置和所属类型。只有这些证据与字典一致时才显示 CSV 值。同一处代码如果仍可能对应多个字典目标，系统会隐藏结果并说明证据不足，不会选第一个碰运气。

用户修改尚未保存的代码时，当前文件的旧结果会马上失效，稍后按编辑器中的新内容重新确认。不会继续显示修改前的旧匹配。

## 6. 缓存和大型项目性能

工具不扫描、也不长期缓存整个大型代码仓。

- 只处理当前真正显示在编辑器里的 C/C++ 文件；左右分屏时处理两个；
- 用户可以同时开很多标签页，但不在屏幕上的文件可释放代码分析缓存，再次切回来时重新请求；
- 当前屏幕里的文件不会因为过了固定分钟数突然消失；
- 缓存键包含当前文件地址、文档版本、选中字典和字段映射，代码一改就不能误用旧结果；
- 用户点击重新加载字典或重新加载 CSV 时，旧分析结果和历史数据缓存一起失效；
- 磁盘上的字典和 CSV 原文件永远不会被缓存清理机制删除；
- 结束展示只隐藏界面数据，不删除用户选择和原文件；关闭编辑器后，下次未重新开始展示时不会擅自显示旧值。

这样把工作量限制在“用户正在看什么”，而不是项目一共有多少万文件。

## 7. Web 与原编辑器窗口怎样绑定

从某个编辑器窗口点击“打开网页工作台”时，后台为这个窗口保存一个临时会话号，网页地址也带上该会话号。

- 网页查询函数关系时，后台只向这个会话对应的窗口发请求；
- 网页点击函数节点时，只按需增加这一层关系，不一次加载全仓；
- 点击“在当前编辑器中定位”时，定位请求仍发回原窗口；
- 不使用容易另开窗口的 `vscode://` 系统级链接；
- 窗口离线、响应超时或语言服务没有返回证据时，网页明确说明真实状态，不画假的连线。

## 8. 扩展为什么提供两个包

两个 VSIX 来自同一份源码、同一版本、同一功能，用户只安装一个：

- **默认右侧栏版**：使用较新的编辑器右侧栏能力，优先安装；
- **兼容布局版**：默认版被拒绝安装，或重新加载后仍找不到“历史诊断”时使用；入口退到兼容性更好的活动栏，所以可能显示在左侧。

兼容布局版不是“少功能版”，但它只能解决扩展清单和面板布局的兼容；定制编辑器实际提供多少代码语义能力，仍以自动检测为准。无论面板入口在哪，兼容性详细报告都会在代码右边单独打开。EXE 不负责安装或猜测扩展是否成功。

## 9. 产品功能模块是什么

这里的“模块”不是一个文件夹，也不是编译出来的库。它是**用户眼里产品的一项真实能力**，范围由用户定义，通常包含一组共同完成这项能力的函数。

例如能源产品中的“为各条母线计算并下发分配值”，可以是一个模块；它可能横跨多个目录、类和几十个函数。以后模块页会保存用户确认的入口函数、相关函数、输入输出、字段证据和说明。函数调用图服务于模块，但模块不由目录结构自动决定。

## 10. 当前已做与暂不做

当前已落地：

- 编辑器窗口注册与 Web 窗口绑定；
- 后台到指定编辑器窗口的语义请求与响应通道；
- 基于编辑器证据的字段匹配和行末历史值；
- 当前函数的一层调用关系，以及网页点击节点后按需展开；
- 自动兼容性检测、短结论、详细解释和诊断信息复制；
- 默认右侧栏与兼容布局两种 VSIX；
- 字典、CSV、后台、Web、扩展和 MCP 分开安装与构建。

当前明确不做：

- 编辑器关闭时仍独立完成高精度代码语义分析；
- 一次性载入整个大型项目的全量函数图；
- 没有动态 Trace 时声称静态调用图就是真实执行路径；
- 根据编辑器名字或某个固定扩展 ID 直接宣布兼容；
- 没有足够类型证据时猜字段映射。

后续再逐步增加函数证据页、用户自定义模块和动态 Trace。每一层都继续遵守同一原则：事实有来源，证据不足就明说。
