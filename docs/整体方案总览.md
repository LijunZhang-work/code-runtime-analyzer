# C/C++ 代码与 CSV 运行日志融合诊断工作台

## 1. 产品定义

这是一个面向 C/C++ 产品历史运行问题的诊断工作台。它以源代码为入口，将 CSV 中保存的历史运行数据按字段和时间映射回代码上下文，帮助开发人员在排查故障时快速建立“代码逻辑—变量状态—时间变化”的证据链。

它不是新的代码编辑器，也不是单纯的 CSV 浏览器。VS Code、Web 工作台、本地分析后端和 AI 服务共同组成一个系统，各自负责最适合的任务。

**核心价值：** 开发人员不必在代码和多个 CSV 之间反复切换、手动搜索并猜测字段关系；系统将经验证的代码关系和数据来源组织起来，让每一个显示值、推断和建议都能追溯到具体代码、CSV 列和时间点。

## 2. 要解决的问题

现有排查过程通常是：根据测试反馈猜测模块，阅读相关函数，手工找出字段，再到多个 CSV 中搜索字段和故障时间，最后回到代码判断条件、循环与调用关系。这种做法存在以下问题：

- 代码、CSV 和时间点割裂，证据链靠人工在脑中拼接；
- 同一字段需要在多个 CSV 中反复检索；
- 很难一次看清一个函数关联的全部字段及其故障前后状态；
- 结构体数组、循环索引和同一实例的多字段关系不直观；
- 大型项目无法依靠人工通读来建立全局理解；
- 每次问题定位都会重复执行字段关联和时间对齐工作。

## 3. 目标、边界与原则

### 3.1 产品目标

1. 自动建立 C/C++ 中函数、结构体、字段、简单数组访问及其调用关系的索引。
2. 导入多份 CSV 并明确统一时间轴和查询语义。
3. 建立代码字段与 CSV 列之间的可追溯映射。
4. 在选定的历史时间点或窗口中，将相关字段值呈现在代码、函数和调用关系上下文中。
5. 逐步扩展至函数证据、局部调用图、功能块和动态 Trace 叠加。
6. 向 AI 提供受控、结构化且有出处的证据包，使其负责解释和排查建议，而非猜测事实。

### 3.2 非目标

- 不替代 VS Code、调试器或 CSV 原始查看工具；
- 不在无动态 Trace 的情况下宣称重建了真实执行路径；
- 不要求为了排查历史问题重新修改、编译或烧录程序；
- 不把全量源码或全量 CSV 直接交给 AI；
- 不将 AI 推断包装成代码事实或日志事实。

### 3.3 设计原则

- **静态事实优先：** 使用 Clang、clangd、libclang、Tree-sitter、Ctags 等成熟工具提取语义或语法事实，AI 不负责识别字段身份。
- **以局部问题为中心：** 用户指定模块、目录、文件、入口函数、时间点或窗口，系统围绕该范围构建局部证据。
- **证据可追溯：** 每个值均能回到运行记录、CSV 文件、列名、采样时间和匹配方式。
- **不确定性可见：** 最近采样、插值、文本推断、可能调用和回调候选必须明确标记，不能伪装为精确事实。
- **渐进式建设：** 先完成代码行级闭环，再做函数、调用图、功能块与动态 Trace。

## 4. 总体架构

```text
VS Code 扩展                         Web 诊断工作台
代码行历史值、Hover、CodeLens          函数证据、调用图、功能块、证据链
          │                                      │
          └──────────── 本地分析与证据服务 ───────┘
                   代码索引 / CSV 时序 / 字段映射 / 查询 API
                                      │
                         AI 诊断服务（可选增强）
                    基于证据包解释、归纳、建议下一步
```

### 4.1 VS Code 扩展

负责开发人员的代码行级交互：取得当前文件、光标和函数；选择运行记录与时间点；显示行内历史值、Hover 趋势、CodeLens 和右键入口；向后端请求结构化数据。扩展不承担复杂的代码分析和 CSV 大数据处理。

### 4.2 本地分析与证据服务

这是系统的核心，负责扫描项目与解析编译信息，建立符号和字段访问索引；导入多份 CSV，统一时间轴；维护字段映射；按时间点、时间窗口和字段身份查询数据；生成供 VS Code、Web 和 AI 消费的稳定接口。

### 4.3 Web 诊断工作台

适合展示跨函数、跨文件、跨模块的信息：局部有向调用图、函数读写字段、字段异常窗口、模块数据流以及已确认的功能块。调用图应是可折叠有向图，而不是强制树形图，以适应共享调用、递归、回调和异步路径。

### 4.4 AI 诊断服务

AI 接收由后端生成的诊断证据包，例如当前问题说明、代码片段、字段读写、时间窗口中的真实值、相关分支、上下游函数、CSV 来源和置信度。AI 输出的是解释、异常传播假设和下一步检查建议，且每条结论应引用相应证据。第一版采用“后端准备证据、AI 单向解释”的闭环；后续再考虑工具调用式 Agent。

## 5. 关键数据与事实分层

系统需要在模型和界面中强制区分以下五类内容：

| 类型 | 含义 | 示例 |
|---|---|---|
| 代码静态事实 | 由语义/语法分析得到 | `bossInfo[i].bossId` 出现在条件表达式中 |
| CSV 数据事实 | CSV 直接记录的值与时间 | `BOSS_2_BOSS_ID=17`，采样于 10:01:03.250 |
| 映射规则 | 两者对应的依据 | 配置规则将 `BOSS_2_BOSS_ID` 映射为 `bossInfo[2].bossId` |
| 工具推断 | 有明确算法但非直接事实的结果 | 当前循环的可能匹配索引为 2 |
| AI 建议 | 基于证据的解释或排查方向 | 建议检查 `targetId` 来源及上一层状态更新 |

该分层是避免误导的基础，尤其适用于时间近似、名称规则映射和静态调用分析。

## 6. 关键能力设计

### 6.1 代码静态分析

后台自动发现 `compile_commands.json` 并使用其真实编译参数，用户不维护机器相关路径。0 个候选时明确提示缺失，唯一候选时使用，多个不同候选时停止并要求选择构建上下文。随后逐步获得函数定义与引用、类型与结构体定义、字段访问、数组下标、简单循环变量、函数调用以及字段的读写角色。

分析结果必须记录来源位置、分析器和置信度。复杂宏、函数指针、跨线程写入、深层指针别名、动态容器和复杂模板可以先标为“未完全解析”，而不能假装准确。

### 6.2 CSV 与时间轴

一个运行记录可以包含多个 CSV。每个 CSV 需要有时间列规则、时间格式、时区、采样周期和重复时间处理策略。查询结果至少区分：

- 精确命中；
- 最近采样值（含采样时间及偏差）；
- 区间聚合值；
- 插值结果；
- 无可用数据。

不同 CSV 的时钟偏移、精度差异、缺失行和重复时间应在导入阶段被检查并报告。

### 6.3 字段映射

字段映射由后台内置的产品字典提供。后台扫描 `backend/dictionaries/*.csv`，一个文件是一套字典；产品 A/B 分开维护，不使用 manifest。固定五列为 `data_source,data_field,target_kind,target,definition_path`，目标类型只有 `time/member/symbol`。

成员身份使用完整 `QualifiedType::field`，不依赖局部变量名；数组宽表通过 `data_field` 中唯一的 `{index}` 展开。全局量使用完整限定符号。`definition_path` 指向仓库内真实定义文件，保证字典不依赖任何电脑的绝对目录。

用户在右侧面板选择字典和一个含多份标准 CSV 的文件夹。`data_source` 以第一层精确文件名匹配且区分大小写；标准 CSV 没有 sheet。0 个候选明确缺失，1 个采用，多于 1 个报告歧义并停止。

### 6.4 数组、结构体和循环

第一优先级场景是普通结构体数组和简单 `for` 循环。系统要能够表达 `bossInfo[i].bossId` 与 `bossInfo[i].status` 属于同一个元素，并在已知 CSV 实例数据时提供“匹配索引”和同实例字段摘要。复杂索引只应展示可确认部分和限制说明。

## 7. 用户工作流

1. 打开代码仓，在右侧面板选择对应产品字典。
2. 一次选择本次运行包含多份 CSV 的文件夹。
3. 选择故障时间点或时间窗口。
4. 在 VS Code 中打开函数，查看相关字段的历史值及其数据来源。
5. 对关键字段查看 Hover 趋势、相邻实例或完整时间序列。
6. 打开函数证据面板，检查字段读写、条件判断与异常变化。
7. 在需要时转入 Web 查看局部调用图和跨函数证据链。
8. 请求 AI 基于当前证据解释现象并建议下一步，而非直接索取根因结论。

## 8. 演进路线

| 阶段 | 主要交付 | 用户收益 |
|---|---|---|
| 阶段一 | 代码行历史值回放、字段趋势、数组/简单循环、映射与溯源 | 不再手工跨 CSV 搜索字段 |
| 阶段二 | 函数证据面板、字段读写、关键判断、AI 函数级解释 | 快速了解函数在故障窗口的相关状态 |
| 阶段三 | 局部调用图与 VS Code/Web 双向定位 | 建立跨函数的可能传播路径 |
| 阶段四 | 人工确认的功能块、输入输出与模块数据流 | 沉淀系统级领域知识 |
| 阶段五 | 动态 Trace 叠加 | 区分可能路径与实际执行路径 |

## 9. 主要风险与控制措施

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 时间轴不一致 | 值被错配到故障时刻 | 明确查询语义、保留偏差、导入时检测时钟和缺失问题 |
| 同名字段 | 映射到错误对象 | 使用完整字段身份；低置信度映射需人工确认 |
| 静态调用不等于真实调用 | 误判故障路径 | 使用“直接/可能/回调候选/无法解析”标签 |
| 信息量过大 | 界面难以使用 | 默认仅展示当前函数、当前时间、变化字段和判断相关字段 |
| AI 结论过度确定 | 降低诊断可信度 | 将建议与事实分层，要求引用代码和 CSV 证据 |

## 10. 成功标准

系统成功的最小标志不是自动找到全部根因，而是开发人员能在真实故障样本中，稳定完成：从代码函数出发，在目标时间点看到正确的关联字段值、结构体数组实例关系、前后变化趋势和可追溯 CSV 来源，并据此减少手工跨文件检索。
