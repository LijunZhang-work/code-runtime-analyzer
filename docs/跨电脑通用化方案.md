# 跨电脑通用化方案

这篇文档回答一个问题：怎样保证工具不是“只在开发者电脑上能跑”，而是换一台全新的电脑仍然能安装、能发现问题、能恢复。

## 先说清当前支持范围

当前正式安装包面向 **64 位 Windows 10、Windows 11 和相应的 Windows Server**。这是因为安装包自带 Node.js 24 运行环境；Node.js 官方把 Windows 10 / Server 2016 及以上的 x64 系统列为受支持平台。

普通用户使用 EXE 和 VSIX时，不需要自己安装 Node.js、npm、WSL、Clang 或 `compile_commands.json`。公司定制编辑器必须兼容 VS Code 扩展接口；编辑器真正能提供多少定义、类型、引用和调用关系能力，由扩展安装后的实际请求检测决定，不能仅凭编辑器名称判断。

## 0.10.2 已经补上的通用能力

1. **EXE 与编辑器彻底分开**：EXE 只安装独立后台、Web、控制中心、自带运行环境和字典；不携带 VSIX/MCP，也不查找、安装、卸载或修改任何编辑器。
2. **没有“选择安装扩展”的页面**：EXE 安装过程不再出现组件选择页，避免用户误以为它会处理编辑器。
3. **登录后自动启动后台**：安装程序使用当前用户的 Windows 启动文件夹，不要求管理员权限，也不依赖可能被公司策略禁用的 Windows Script Host。
4. **只安装 VSIX 也不反复报错**：扩展默认先找独立后台，找不到时使用扩展自带后台；后台后来恢复时会自动重连。
5. **一键导出诊断报告**：后台控制中心可以生成 `%LOCALAPPDATA%\CodeRuntimeAnalyzer\diagnostic-report.json`，报告会区分安装不完整、后台没响应、端口冲突和版本不匹配，并把用户目录替换成环境变量名称。
6. **日志不会无限增长**：后台启动时会把超过 2 MB 的旧日志轮换为一份 previous 文件，只保留当前和上一份。
7. **真实安装测试**：GitHub 发布前会在一次性的 Windows 虚拟机中静默安装 EXE，检查健康接口、诊断导出、重复安装、卸载和登录启动项，并比较安装前后的编辑器扩展目录，任何一项不对都不发布。
8. **安装包内容防回归**：本地构建和 GitHub 构建都会检查 EXE 中没有 VSIX/MCP，两个 VSIX 均带有备用后台且默认自动连接。
9. **原生后台控制中心**：控制中心已经是独立的 Windows GUI 程序，提供状态、启动、停止、重启、打开 Web、日志和诊断导出；安装目录不再包含 VBS，也没有引入 Electron 或额外 .NET 运行时。
10. **大型项目性能门禁**：每次发布都会测试 250、2500、10000 个代码文件三档工程，并检查首次分析、缓存分析、内存、当前文件文档数和缓存数；每周还会在固定版本的 OpenCV 真实项目上复测。

微软把 Windows Sandbox明确定位为干净环境中的软件测试工具；GitHub 的 Windows 托管运行器也是每个任务重新创建的虚拟环境。因此自动发布用 GitHub Windows 虚拟机做硬性门禁，发布前还可以用 Windows Sandbox 做一次人工界面验收：

- [Windows Sandbox 官方说明](https://learn.microsoft.com/windows/security/application-security/application-isolation/windows-sandbox/)
- [Windows Sandbox 配置文件示例](https://learn.microsoft.com/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-sample-configuration)
- [GitHub Windows 托管运行器](https://github.com/actions/runner-images)

## 仍然缺少、值得继续开发的能力

### 第一优先级：发布可信度

#### 1. 给 EXE 做可信代码签名

0.10.2 已经接好严格的 Authenticode 发布流程：后台控制中心、NSIS 内部卸载程序和最外层安装程序都会使用 SHA-256 与时间戳签名，并在创建 Release 前复验。证书或密码缺失时工作流会失败，不会悄悄发布未签名 EXE。

推荐顺序：

1. 公司内部使用：让公司 IT 用企业证书签名，并通过公司策略信任；
2. 公开开源发布：确认项目许可证后申请 SignPath Foundation 免费开源签名；
3. 商业公开发布：使用 Microsoft 推荐的 Artifact Signing 或可信 CA 代码签名证书。

微软明确要求可部署的 MSIX 必须签名且证书受目标电脑信任；对普通 EXE，可信签名同样是减少 SmartScreen 和企业拦截的关键。参考：

- [Microsoft：Windows 应用代码签名方案](https://learn.microsoft.com/windows/apps/package-and-deploy/code-signing-options)
- [SignPath Foundation：开源项目免费代码签名](https://signpath.org/)

**发布前仍需完成的外部条件**：项目所有者需要取得受信任的 Authenticode 证书，并把 PFX 的 Base64 与密码分别放进 GitHub Actions Secrets。仓库目前也没有 `LICENSE`；如果选择 SignPath Foundation 免费开源签名，还必须先由项目所有者确定 MIT、Apache-2.0 或其他 OSI 认可许可证。签名私钥、PFX 和密码永远不能进入 Git 历史或 Release 附件。

同时还应补一份第三方依赖清单 / SBOM 和隐私说明，让公司安全人员能够确认安装包包含什么、工具默认不向外网发送源代码或 CSV。这个工作适合接入成熟的 CycloneDX 或 GitHub 供应链能力，不应手工维护一份很快过期的依赖表。

#### 2. 发布包必须与源码标签一致

不能修改同一个版本号下面已经发布的二进制文件来“偷偷换包”。每次修复安装行为都应该生成新的补丁版本，例如从 `0.10.0` 到 `0.10.1`，标签、源码版本、EXE、VSIX、MCP 和校验文件必须全部一致。

### 第二优先级：连接和安全

#### 3. 固定端口改成“自动发现 + 冲突回退”

独立后台把 `127.0.0.1:47831` 当作首选端口，不再把它当成必须占用的固定端口。如果这个端口已被公司软件占用，后台会自动寻找下一个可用端口，不要求用户改配置。

后台每次启动还会生成一枚随机的本机访问密钥，并把实际地址、端口和密钥写入当前 Windows 用户自己的 `%LOCALAPPDATA%\CodeRuntimeAnalyzer\service-state.json`。VS Code 扩展和直接运行在 Windows 中的 MCP 会自动读取；从网页复制给 WSL OpenCode 的配置会同时带上当次实际地址和密钥。后台重启后旧密钥自动失效，诊断报告和普通状态输出不会泄露密钥。

这项能力已经实现，并由自动化安装测试故意占用 47831 后验证：后台仍能换端口启动，未携带或携带错误密钥的请求会被拒绝。

#### 4. 不依赖 VBS 的原生后台控制中心（已经完成）

后台控制中心已经替换为约 0.8MB 的原生 Windows GUI 程序。用户可以看见后台是否正常运行，并直接点击按钮操作；窗口最小化后保留托盘图标。它不使用 VBS、Electron 或额外 .NET 运行时。发布校验会拒绝任何重新混入 VBS 的安装包。

WinSW 是成熟的 Windows Service Wrapper，但安装系统服务通常需要管理员权限，并会增加公司环境审批成本，所以目前不作为默认方案，只适合作为公司 IT 集中部署时的可选模式：[WinSW 项目](https://github.com/winsw/winsw)。

### 第三优先级：更多机器和更多项目

#### 5. 增加 ARM64 安装包

Node.js 官方把 Windows x64 列为 Tier 1、Windows ARM64 列为 Tier 2。当前 EXE 明确是 x64 包；Windows 11 ARM 的 x64 模拟通常可运行，但不能把“通常可以”冒充原生支持。需要真实 ARM64 机器或 ARM64 CI 后，再发布独立的 ARM64 包。

- [Node.js 官方支持平台](https://github.com/nodejs/node/blob/main/BUILDING.md#supported-platforms)

#### 6. 建立编辑器兼容矩阵

VS Code 扩展清单中的 `engines.vscode` 本来就表示扩展兼容的编辑器版本范围。我们已经提供默认版和兼容布局版，但还需要在标准 VS Code 的最低兼容版本、当前稳定版以及至少一种公司定制版上保存真实检测结果。

- [VS Code 官方 Extension Manifest 说明](https://code.visualstudio.com/api/references/extension-manifest)

#### 7. 大型项目性能基准（第一版已经完成）

发布前固定测试 250、2500、10000 个代码文件三档规模，记录首次分析、重复分析和 Node + clangd 的内存，并硬性确认只保留当前文件的 clangd 文档和代码缓存。当前电脑第一次实测分别约为 196ms、917ms、8568ms，缓存分析均约 2ms，最大档约 127MB；这些数据是基线，不代表所有电脑都必须一样快。每周的独立工作流还会下载固定版本 OpenCV，生成真实编译数据库并测试一个当前文件，报告单独保存。

下一步仍需增加“切换多个可见文件”和“修改头文件后的准确失效”两类性能场景，但不会为了速度继续显示已经失效的缓存。

### 第四优先级：产品能力

在通用安装稳定后，再继续开发这些用户能力更划算：

1. 两个时间点的历史值对比，直接显示哪些字段发生变化；
2. 用户自定义“产品功能模块”，把一组真实业务函数组织成一个模块；
3. 函数调用图按方向、深度、模块和外部函数过滤，避免大型项目过于杂乱；
4. 字典可视化校验，导入前逐行告诉用户缺列、路径错误或歧义；
5. AI 可以建议字典映射和模块边界，但必须由用户确认后才能成为正式映射，不能把猜测当事实。

## 推荐开发顺序

```text
新发布包 0.10.2
  → 可信代码签名 / LICENSE 决策
  → 自动端口发现 + 本地访问令牌
  → ARM64 与编辑器兼容矩阵
  → 扩充大型项目切换/修改场景
  → 时间点对比、产品模块和 AI 辅助
```

这个顺序先解决“换电脑装不上、出了错不知道为什么”，再扩展业务功能，避免功能越来越多但交付仍不可靠。
